# Auditoria funcional e de dados — 25/09/2026

## Escopo verificado

- contratos entre a interface, os schemas Zod, os tipos TypeScript e as RPCs;
- isolamento por workspace, RLS e concorrência otimista nas mutações centrais;
- compatibilidade da interface com migrations ainda não publicadas;
- tarefas, checklist, tarefas vinculadas, Kanban, semana, projetos, perfil e configurações;
- lint, typecheck, testes unitários e build de produção.

## Resultado

O código local compila e os testes automatizados passam. Todos os nomes de RPC
usados em `features/**` têm uma definição em alguma migration local. As tabelas
centrais têm RLS e as mutações principais de tarefa usam RPC e versão.

Isso não comprova que o schema hospedado está atualizado. A inspeção do projeto
Supabase vinculado falhou com `403 LegacyDbConfigLoginRoleStatusError`: a conta
atual não possui os privilégios necessários para consultar ou publicar o
histórico remoto de migrations.

## Correções aplicadas nesta auditoria

1. **Capacidades opcionais de tarefa**
   - A interface não usa mais `can_edit` como autorização implícita para criar
     tarefas vinculadas.
   - Checklist rápido, tarefas vinculadas e seus controles só aparecem quando o
     payload do backend informa suporte.
   - Exclusão de passos/seções e desvinculação receberam uma capacidade própria,
     detectada pela existência das RPCs da migration de gerenciamento.

2. **Perfil e configurações do workspace**
   - Os fallbacks legados agora são somente leitura.
   - A interface explica quando a edição depende de uma migration ainda não
     publicada, em vez de aceitar dados e falhar apenas no envio.

3. **Kanban**
   - Se `move_task_in_board` ainda não existir, mover entre status usa
     `update_task` como fallback versionado.
   - Reordenação dentro da mesma coluna informa que depende da atualização do
     backend e restaura a posição anterior.

4. **Semana e calendário**
   - Os dois fluxos de mover para uma data agora usam `move_task_in_week` com
     `week_lane='scheduled'`, mantendo faixa, data e posição coerentes.

5. **Isolamento da sessão**
   - O detalhe de tarefa rejeita payload cujo `workspace_id` seja diferente do
     workspace selecionado.

6. **Projetos**
   - O diálogo de tarefa não oferece status bloqueado sem possuir um campo para
     o motivo obrigatório.
   - Projeto vazio e sem avaliação manual exibe “Sem avaliação”, em vez de
     afirmar que está saudável sem dados.
   - O detalhe passou a invalidar seus dados em alterações Realtime de projeto,
     tarefas, marcos e equipe.

7. **Realtime das tarefas**
   - O quadro invalida métricas quando checklist ou comentários mudam.
   - O detalhe do pai invalida quando a relação com uma tarefa vinculada muda.

## Pendências de banco e arquitetura

### Bloqueio de publicação remota

Pelo estado documentado do projeto, estas migrations continuam locais e devem
ser publicadas em ordem, com smoke autenticado depois de cada etapa:

- `20260924213000_task_steps_and_subtasks.sql`;
- `20260925103000_profile_identity.sql`;
- `20260925120000_workspace_settings.sql`;
- `20260925130000_task_board_ordering.sql`;
- `20260925150000_task_steps_management.sql`.

A fundação `20260824090000_team_operating_model_foundation.sql` também permanece
local e não deve ser tratada como autorização efetiva no produto hospedado.
O histórico disponível também não permite confirmar remotamente
`20260924193000_task_custom_fields.sql`; a interface mantém essa capacidade
desativada quando o payload não a anuncia.

### Itens que exigem uma migration posterior

- Incluir `workspace_id` explicitamente nas assinaturas dos RPCs por entidade,
  sobretudo detalhe/edição de tarefa, mantendo validação composta no banco. A
  barreira atual da interface impede mistura visual, mas o contrato definitivo
  deve carregar o workspace em toda leitura e escrita.
- Substituir o enum legado de seis fases de marco por etapas de projeto criadas,
  ordenadas e removidas pelo usuário. A interface não presume fases, mas o banco
  ainda persiste o valor técnico `preparation`.
- Adicionar versão ou `updated_at` esperado ao toggle de checklist para evitar
  que duas sessões sobrescrevam silenciosamente o estado uma da outra.
- Regenerar `lib/database.types.ts` a partir do schema publicado. Alguns RPCs de
  Recursos ainda usam casts manuais, e `set_task_primary_assignee` precisa
  representar `p_user_id` como `string | null`.

### Funcionalidades que não devem ser anunciadas como concluídas

- notificações do navegador e sons estão salvos como preferência, mas ainda não
  controlam o menu ou um serviço de notificação;
- a preferência de densidade grava `data-pta-density`, mas ainda não possui uma
  camada CSS completa que altere a interface.

## Evidência local

- `pnpm lint`: aprovado;
- `pnpm typecheck`: aprovado;
- `pnpm test`: 42 arquivos e 242 testes aprovados;
- `pnpm build`: aprovado no Next.js 16.3.1.

O próximo checkpoint confiável é publicar as migrations com uma conta Supabase
autorizada, regenerar os tipos e executar o smoke autenticado contra o schema
hospedado. Até isso acontecer, os fallbacks mantêm a interface honesta e evitam
ações que certamente falhariam.
